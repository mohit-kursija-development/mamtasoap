# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static single-page marketing site for **Mamta Soap Works**, served by GitHub Pages at `mamtasoapworks.com` (see [CNAME](CNAME)). There is no build system, package manager, test suite, or linter — the deployed artifact *is* the source.

## Commands

There is nothing to build or install. To develop:

```bash
# Preview locally (any static server works; needed because relative asset paths
# and the CDN <link>s behave best over http:// rather than file://)
python3 -m http.server 8000
```

Deploy = commit and push to the `single_page` branch. GitHub Pages picks it up directly; there is no CI step.

## Branch layout — important

The two branches are **different applications**, not versions of each other:

- **`single_page`** (current, deployed): the static site. Everything is [index.html](index.html) + [css/common.css](css/common.css) + [images/](images/).
- **`main`** (legacy, not deployed): the original Flask app — `main.py` with a `/` route rendering `templates/index.html` from a Python `cards` list, plus an `/api/submit-form` SMTP endpoint. Assets live under `static/`.

Do not merge or rebase between these branches; a diff between them is ~100 files of unrelated restructuring. Note that `origin/HEAD` points at `main`, so PRs default to the wrong base — target `single_page` explicitly.

## Architecture

Two files carry the whole site: `index.html` (markup + one inline `<script>`) and `css/common.css` (design system + every component).

**No JS libraries.** Everything is vanilla JS in a single IIFE at the bottom of `index.html`. Bootstrap, jQuery and animate.css were all removed in the 2026 redesign — do not reintroduce them. The only remote assets are Google Fonts and the bootstrap-icons *font* package (`<i class="bi bi-*">`), both plain CDN `<link>` tags.

**Progressive-enhancement guard — read before touching animations.** The script's first statement is `document.documentElement.classList.add("js")`. Every "hidden until animated" start state in the CSS is scoped to `.js` (`.js [data-reveal]`, `.js .product.is-entering`, `.js .rule`, `.js .hero__title .line > span`, `.js .process__steps::before`). This is deliberate: if the script never runs or throws, the page renders fully visible instead of leaving whole sections stuck at `opacity: 0`. **Any new reveal-style animation must follow the same pattern** — put the hidden state under `.js`, never bare.

For the same reason the hero stat figures (`48+`, `13`, `4`, `100%`) are the real values in the markup; JS zeroes them at startup and counts back up when they scroll into view.

**Scroll reveal.** Add `data-reveal` to any element (`data-reveal="left" | "right" | "scale" | "fade"`, default is up) and `style="--d:120ms"` to stagger it. One shared `IntersectionObserver` adds `.is-visible` and unobserves.

**Product catalogue — markup is the source of truth.** The 13 products are real `<article class="product">` elements in `#productsGrid`, *not* generated by JS. This is deliberate and load-bearing for SEO: they are the page's primary commercial content and must be indexable without a crawler executing JS. (They used to live in a `cards` array; "RK Washing Soap" then appeared zero times in crawlable text.)

The script reads that DOM once into a `cards` array (`node`, `image`, `alt`, `title`, `desc`, `category`, `items`) and uses it for filtering and the lightbox. To add, remove or reorder products, **edit the HTML** — then run `tools/seo-sync.py` (below). Filter chips and their counts are static markup too; update them by hand when a category's product count changes. Filtering toggles the `hidden` attribute and replays a staggered fade-in; the lightbox cycles through the currently *filtered* set.

**FAQ** is plain `<details class="faq__item">`/`<summary>`, so the answers are in the DOM, crawlable and keyboard-accessible with no JS. Each `<summary>` wraps its text in `<span class="faq__q">` — required, because `summary` is a flex container and any bare inline `<span>` would otherwise become a gap-separated flex item ("Is RK ⎵ sabun ⎵ a Jain soap?").

**Marquee.** The first `.marquee__group` is real markup (so it reads correctly with JS off and is indexable); the script clones it once to make the `-50%` scroll loop seamless, and marks the clone `aria-hidden`. Edit the items in the HTML, not the JS.

**Contact form.** `#callbackForm` POSTs natively to `https://formsubmit.co/<email>` with hidden `_subject` / `_captcha` / `_template` / `_next` fields plus a `_honey` honeypot. The submit handler validates name (`/^[A-Za-z ]+$/`), phone (`/^\d{10}$/`) and a non-empty query, and only calls `event.preventDefault()` on failure — on success it deliberately falls through to the browser's native submission. Errors render inline via `.field.is-invalid` + the `data-error` attribute (there is no popup div any more). `_next` sends the visitor back to `/?sent=1`, which the script turns into a success toast before cleaning the URL.

**Sections** are `#home`, `#about`, `#why`, `#products`, `#faq`, `#contact`, linked from the fixed navbar and tracked by a scroll-spy observer.

## SEO — what must stay true

The site ranks on being a crawlable, richly-marked-up single page. Three things have to agree, and they will silently drift if edited by hand:

| Source of truth in `index.html` | Derived artefact |
| --- | --- |
| `<article class="product">` cards | `ItemList` / `Product` JSON-LD |
| `<details class="faq__item">` entries | `FAQPage` JSON-LD |
| every `<img>` with a real `alt` | `<image:image>` entries in `sitemap.xml` |

**After editing products, FAQ entries or image alt text, run:**

```bash
python3 tools/seo-sync.py
```

It rewrites the `<script type="application/ld+json">` block in `index.html` and regenerates `sitemap.xml` from the markup. It is idempotent and touches nothing else. The site deploys fine without ever running it — it is a consistency tool, not a build step.

Other things not to regress:

- **One `<h1>`**, and it carries the primary keywords. The display lines ("Tough on stains. / Gentle on fabric.") are followed by `<span class="hero__title-sub">` inside the same `<h1>`, which is where "RK washing soap", "sabun" and "Ulhasnagar" live. Styled as body copy so the design still reads as a display headline.
- **Target keywords** are English *and* Hinglish: `RK sabun`, `RK washing soap`, `kapde`, `bartan`, `Jain soap`, `washing soap manufacturer Ulhasnagar`, `dishwash gel`, `detergent powder`, `fabric cleaner`, `wholesale`/`bulk`. Hinglish words are marked `<span lang="hi-Latn">` so they are not read as misspelt English.
- `robots.txt` and `sitemap.xml` sit at the repo root and are served from the domain root by GitHub Pages. The `Sitemap:` line in robots.txt must stay absolute.
- `<link rel="preload" as="image" href="images/rk_soap.jpeg" fetchpriority="high">` targets the LCP element — keep it pointed at whatever the hero image actually is.
- Product `alt` text is keyword-bearing and unique per SKU; `.brand__mark` and the footer logo are decorative and correctly `alt=""`.

## Conventions

- **Design tokens live in `:root`** at the top of common.css. The four brand hexes are unchanged from the original site and must stay exactly: `#44548c` navy, `#fbf1e9` cream, `#FF885B` orange, `#ff0000` red. Everything else (`--navy-deep`, `--ink`, `--cream-hi`, …) is a tint or shade mixed from those four — derive new colours from them rather than introducing a new hue.
- **Fonts** are Fraunces (display/headings, `--font-display`) and Plus Jakarta Sans (body/UI, `--font-body`). Both are variable fonts loaded from Google Fonts.
- **Class naming is BEM-ish** (`.hero__frame`, `.product__media`, `.nav__link`, `.contact-card__label`) with a few shared primitives: `.container`, `.section`, `.section-head`, `.btn` (+ `--ghost`, `--accent`, `--sm`), `.eyebrow`, `.lede`, `.cards-grid`, `.chip`, `.spec`. Prefer extending these over inline styles.
- **Spacing is CSS, not `<br/>`.** The old markup used literal `<br/>` tags for vertical rhythm; that is gone. Use the section/grid gap system.
- **`img { height: auto }` in the base reset is load-bearing.** Several images carry `width`/`height` attributes, and without `height: auto` that attribute beats any `aspect-ratio` you set — this previously rendered the hero image at 1280px tall. If you give an image an `aspect-ratio`, make sure nothing re-fixes its height.
- **`display` beats `[hidden]`.** `.product` and `.lightbox` set `display: flex`/`grid`, so each needs an explicit `[hidden] { display: none }` rule. Any new component toggled via the `hidden` attribute needs the same.
- **Image filenames contain literal spaces and inconsistent dashes** — e.g. `images/3 -  - 5X7.jpg` (space-dash-two spaces-dash-space) versus the outlier `images/1--5X7.jpg`. Copy paths verbatim from the directory listing rather than typing them; the `main` branch uses a different `----` convention for the same files.
- **Images are already optimised — do not re-add print-resolution files.** The referenced images were downscaled from up to 5668x4049 to a 1200px long edge (9.6 MB → 1.3 MB). If you add a new photo, run `python3 tools/optimise-images.py` rather than committing the camera original. It only touches images `index.html` actually references, never upscales, never writes a larger file, applies EXIF orientation before resizing, and refreshes the `width`/`height` attributes in the markup afterwards so CLS stays at 0. `--dry-run` reports without writing.
- **`images/` still holds ~29 unreferenced product photos (~17 MB).** They cost nothing at runtime (never fetched) and are left alone deliberately — they are the owner's photo library. `tools/optimise-images.py` skips them by design.
- Below-the-fold `<img>`s carry `loading="lazy" decoding="async"`; keep that on anything new. The hero image must *not* be lazy — it is the LCP element and is preloaded.
- **`width`/`height` attributes must match the file's real pixels.** A stale value is worse than none because it reserves the wrong space. `tools/optimise-images.py` resyncs them; do not hand-edit.
- Responsive overrides sit in `@media` blocks at the end of common.css (1080px, 860px, 720px, 420px); a new sizing rule usually needs a companion entry. A `prefers-reduced-motion` block at the very end disables all animation and force-shows every revealed element — leave it last so its `!important` rules win.
